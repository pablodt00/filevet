    Architecture¶

    This is the design as built so far. The pipeline and contracts are in src/filevet/core/, the analyzers in src/filevet/analyzers/, the verdict policies in src/filevet/policies/, and the CLI and REST API in src/filevet/interfaces/.

    Pipeline¶

    flowchart LR
    In[Untrusted file] --> Ingest
    Ingest[Ingest<br/>size limit, private temp copy, hashes] --> Identify
    Identify[Identify<br/>type from magic bytes] --> Dispatch
    Dispatch[Dispatch<br/>every analyzer whose supports is true] --> W1[Analyzer worker]
    Dispatch --> W2[Analyzer worker]
    Dispatch --> W3[Analyzer worker]
    W1 & W2 & W3 -- findings --> Aggregate
    W1 & W2 & W3 -- extracted children --> Recurse
    Recurse[Recurse<br/>depth, count and size limits] --> Identify
    Aggregate[Aggregate<br/>findings] --> Policy[Policy<br/>overrides, suppressions, verdict] --> Report[Report JSON]
    Aggregate --> Cleanup[Cleanup<br/>delete temp files]
    1. Ingest rejects files over the size limit (50 MB by default) with a usage error, copies the input into a private temp directory, and computes its SHA-256 and MD5. Each copy is created 0600 and made read-only (0400) before any analyzer sees it.
    2. Identify detects the type from magic bytes with the built-in signature table in core/identify.py (see ADR 9), and takes the declared type from the extension. If the two contradict each other, basic.type_mismatch reports it.
    3. Dispatch runs every analyzer that supports the artifact, each in its own worker.
    4. Recurse feeds extracted children (archive entries, PDF attachments, embedded OLE objects) back into Identify, within max_depth, max_children and max_total_expanded_bytes.
    5. Aggregate collects artifacts, findings and analyzer runs. When a recursion limit is hit, the rest of the extracted content is skipped and the pipeline adds one pipeline.limit_exceeded finding (severity high) per limit.
    6. Policy builds the report from them: it applies severity overrides, moves suppressed findings aside, and sets the verdict (block, review, pass_with_findings or pass) together with the rule that decided it. See policies.md.
    7. Cleanup always deletes temp files, including after errors.

    Core contracts¶

    There are three contracts. Analyzers depend only on these, never on each other.

    Artifact: one file being scanned, either the input or an extracted child. It's immutable and holds an ID, name, size, hashes, declared and detected types, depth, parent ID and a path to a read-only copy. The pipeline owns the file; analyzers only read it.

    Analyzer: a protocol. analyze returns an AnalyzerResult with findings and extracted children. The AnalysisContext it receives holds the limits, the expected values from the --context file (Expected), and whether to mask IBANs in evidence.

    class Analyzer(Protocol):
    name: str
    version: str

    def supports(self, artifact: Artifact) -> bool: ...
    def analyze(self, artifact: Artifact, ctx: AnalysisContext) -> AnalyzerResult: ...

    Finding: one observation. It has a stable namespaced rule_id (parser.csv_formula_injection), title, description, severity (info to critical), confidence, artifact ID, location (page, cell, XPath, byte offset or archive path), evidence of at most 256 escaped characters, references (CVE, CWE, OWASP) and the analyzer that produced it.

    The pipeline stamps each finding with the artifact ID and the analyzer's name and version, so an analyzer only fills in what it observed.

    Findings say what was seen. The policy decides what to do about it (block, review or pass with findings), so changing the policy never means changing an analyzer.

    The JSON schema of the report, which includes Finding and Artifact, is a public contract. It's committed at schema/report.schema.json and printed by filevet schema. A test fails if the two drift apart. All three models are pydantic models (ADR 7).

    Isolation model¶

    Every analyzer run goes through a Sandbox (core/sandbox.py), chosen with FILEVET_SANDBOX or the sandbox= argument. The process handles one artifact and is then killed, so no state leaks between files. Each run has a wall-clock timeout (30 s by default) and a memory cap (1 GB by default, via RLIMIT_AS). The result comes back as JSON, which the pipeline validates against AnalyzerResult before using it. Nothing crosses the boundary as a pickle. If an analyzer times out, crashes, raises, returns something invalid or sends a result that's too large, the scan records a pipeline.analyzer_error finding with severity high and goes on with the other analyzers. Only the exception type goes into the report, never its message, because a message can quote file contents.

    The subprocess backend forks the worker (ADR 6). The nsjail and gvisor backends start a fresh interpreter in a jail with no network, a read-only root holding only the Python runtime, the sample and a small tmpfs, a non-root user with no capabilities, no_new_privs, a seccomp allow-list and limits on CPU, memory, files and processes (ADR 13). What each backend guarantees, and where it stops, is in security-model.md.

    Logs hold hashes, rule IDs and timings only, never file contents.

    Built-in analyzers¶

    Analyzers are grouped in families that match their rule ID prefix: basic, malware, parser, format, integrity and ai. The integrity and AI analyzers share a raw PDF reader (core/pdf.py). The integrity analyzers also use the financial entity extractor in core/extract_finance.py, and are described in integrity.md.

    ai.hidden_content reads text through core/extract_text.py, which turns a PDF, OOXML file or text file into runs of text, each marked as body, metadata or comment and with the reason it's hidden, if it is. The PDF reader records each text run's rendering mode, fill colour and opacity, and where images are drawn, so the extractor can tell invisible, white, tiny, off-page and covered text apart from an OCR layer over a scan. filevet extract runs the same extractor in an isolated worker and prints only the visible runs with --visible-only. Some of them also act as format handlers and return children for the pipeline to scan:

    Analyzer Extracts
    parser.archive ZIP entries, including the parts of OOXML files, within the ratio, size and count limits
    malware.pdf_active_content PDF embedded files
    malware.office_macros OLE Ole10Native packages
    parser.polyglot The second file hidden inside a polyglot

    So a macro in an .xlsm is found in two steps: parser.archive extracts xl/vbaProject.bin, and malware.office_macros reads its VBA when that child comes back through the pipeline. Analyzers read their input with Artifact.read(limit), so every read is bounded. Libraries and the reasons for them are in ADR 10.

    Three environment variables configure them:

    Variable Effect
    FILEVET_CLAMD Address of clamd, unix:/path/clamd.sock or tcp:host:port. Without it malware.clamav doesn't run
    FILEVET_YARA_RULES Extra directories of .yar files, separated by :, loaded next to the bundled rules
    FILEVET_XSD_DIR Directory of ISO 20022 XSDs named <message>.xsd, for example camt.053.001.08.xsd

    Plugin model¶

    Analyzers are found through the filevet.analyzers entry point group. CONTRIBUTING.md shows how to register one.

    Built-in analyzers register the same way as third-party ones, so a separate package can add analyzers without forking filevet (ADR 8). filevet analyzers lists everything registered and the detected types each one supports. It works that out by calling supports() once per known type. The test suite includes a separate example plugin package in tests/plugin/.

    Interfaces¶

    • CLI (interfaces/cli.py): scan, extract, sanitize, policy test, serve, worker and the informational commands. sanitize (filevet/sanitize.py) runs in the same sandbox as the analyzers (sanitize.md). Output formats (SARIF, JUnit XML, Markdown) are in interfaces/formats.py.
    • Library: filevet.scan, filevet.ascan, filevet.extract_text, filevet.sanitize and filevet.Policy. What's public from 1.0 is listed in stability.md. ascan runs the scan in a thread, so the event loop isn't blocked.
    • REST API (interfaces/api.py, FastAPI): small uploads are scanned in the request, larger ones are queued. The queue (interfaces/jobs.py) is a small Backend protocol with a Redis implementation for production and an in-memory one for development (ADR 12). Queued uploads are encrypted with Fernet. Workers run the same pipeline, so the isolation model is the same for every interface. Details are in api.md, and the Helm chart is described in kubernetes.md.
    • LLM second opinion (filevet/llm.py): an optional verifier found through the filevet.llm_verifiers entry point group. It sees one ai.* finding at a time, can only raise its confidence, and is never called unless --llm-verify names it.
